## 一、简历项目文案

### 项目名称

Gzm Design 在线海报设计器

### 项目定位

Gzm Design 是一套基于 Vue 3、TypeScript、Vite 和 Leafer UI 实现的在线海报设计器，支持多页面画布编辑、图层管理、模板导入、PSD 文件解析、富文本编辑、二维码/条形码生成、素材管理、画布缩放拖拽、JSON/图片导出等能力，面向营销物料、海报制作、运营设计等场景。

### 技术栈

Vue 3、TypeScript、Vite、Pinia、Vue Router、Arco Design Vue、UnoCSS、Leafer UI、ag-psd、Axios、MockJS、TinyMCE、fontfaceobserver。

### 简历描述版本 A：偏业务价值

参与开发在线海报设计器 Gzm Design，项目面向运营海报、营销素材和模板化设计场景，提供浏览器端可视化编辑能力。负责编辑器核心模块和交互能力建设，包括基于 Leafer UI 封装画布服务、实现元素添加/选中/缩放/层级管理、多页面工作区切换、模板 JSON 导入导出、PSD 图层解析和字体加载等功能。通过 Vue 3 组件化拆分左侧素材栏、中心画布、右侧属性面板和顶部工具栏，结合 Pinia、事件总线和依赖注入机制降低模块耦合，提升编辑器可维护性和扩展性。

### 简历描述版本 B：偏技术架构

负责 Gzm Design 在线海报设计器前端架构设计与核心能力实现。项目采用 Vue 3 + TypeScript + Vite 构建 UI 层，基于 Leafer UI 封装 `MLeaferCanvas` 画布服务，统一管理画布实例、内容层、编辑画板、选中对象、缩放状态和多页面 JSON 数据。引入类 VS Code 风格的依赖注入体系管理 EventBus、Workspaces、Hierarchy、Keybinding、UndoRedo 等服务，通过事件总线解耦工作区切换、画布数据保存和页面恢复逻辑。实现 PSD 导入解析，将 Photoshop 图层转换为 Leafer 的 Text、HTMLText、Image、Group 等可编辑对象，并通过字体提取和懒加载保证模板渲染一致性。

### 简历描述版本 C：偏个人贡献

在 Gzm Design 项目中主要负责编辑器核心逻辑和复杂交互功能开发：

1. 封装 Leafer 画布服务，统一提供元素添加、选中、缩放、JSON 导入导出、多页面切换等 API。
2. 设计工作区服务和事件总线机制，实现页面切换前保存当前画布、切换后恢复目标页面数据。
3. 开发左侧素材面板、画布挂载组件和右侧属性面板联动逻辑，实现 UI 操作驱动画布对象变化。
4. 接入 PSD 解析能力，完成普通文本、富文本、图片、分组、蒙版等图层向编辑器对象的转换。
5. 优化字体加载流程，支持从模板 JSON 中提取字体并按需加载，减少文本渲染偏差。
6. 通过插件化和依赖注入方式组织编辑器模块，提高复杂编辑器功能的可扩展性。

### 简历描述版本 D：一句话浓缩

基于 Vue 3 + TypeScript + Leafer UI 开发浏览器端在线海报设计器，负责画布服务封装、多页面工作区、图层管理、PSD 导入、模板 JSON 导入导出、字体加载和插件化架构设计。

### 简历项目亮点

1. 不是普通后台页面，而是复杂交互型可视化编辑器。
2. 画布编辑能力封装为服务，Vue 组件只负责触发操作和展示状态。
3. 使用依赖注入管理多个编辑器服务，降低模块耦合。
4. 使用事件总线解耦工作区、多页面和画布保存恢复逻辑。
5. 支持 PSD 导入，把外部设计文件转换为可编辑画布对象。
6. 支持多页面 JSON 数据结构，便于模板保存、导入、导出。
7. 支持富文本、字体加载、二维码、条形码、图片导出等复杂业务能力。

### 面试自我介绍项目版

我最近做的一个比较有代表性的项目是 Gzm Design 在线海报设计器。它不是传统表单型前端项目，而是一个浏览器端可视化编辑器。项目使用 Vue 3、TypeScript 和 Vite 构建 UI，画布核心基于 Leafer UI。我主要关注编辑器核心架构，包括画布服务封装、多页面工作区、图层管理、PSD 导入、模板 JSON 导入导出以及字体加载。整体设计上，我把 Vue 组件和画布逻辑做了分层：Vue 负责左侧素材栏、右侧属性面板、顶部工具栏等 UI，真正的画布操作统一收敛到 `MLeaferCanvas` 服务里；服务之间通过依赖注入和事件总线协作，避免组件直接互相调用。这个项目让我对复杂前端状态、画布编辑器、模块解耦和性能优化都有比较深入的实践。

### 面试回答项目难点版

这个项目最大的难点是编辑器状态复杂。普通页面的状态通常是表单字段和列表数据，但海报设计器里有画布实例、选中对象、图层树、多页面 JSON、缩放比例、工具状态、字体加载状态和导入导出流程。如果这些状态全部散落在 Vue 组件里，会非常难维护。所以我把画布操作封装成 `MLeaferCanvas` 服务，并把工作区、事件总线、层级、快捷键、撤销恢复等能力拆成独立服务。组件通过 `useEditor()` 拿服务，服务之间通过事件协作。比如切换页面时，工作区服务只负责发 `workspaceChangeBefore` 和 `workspaceChangeAfter`，画布服务监听事件后保存旧页面 JSON 并恢复新页面 JSON。这样职责边界更清楚，后续扩展也更稳定。

### 面试回答技术亮点版

技术亮点主要有三个。第一是画布服务封装，我没有让各个 Vue 组件直接操作 Leafer 实例，而是通过统一的 `editor.add`、`importJsonToCurrentPage`、`zoomToFit` 等 API 操作画布。第二是多页面和事件总线设计，页面切换前后通过事件完成数据保存和恢复，减少模块直接依赖。第三是 PSD 导入，项目使用 `ag-psd` 解析 Photoshop 文件，再把 PSD 图层转换成 Leafer 的 Text、HTMLText、Image、Group 等对象，同时处理字体、颜色、描边、段落样式等属性转换。

## 三、面试回答建议

### 1. 回答顺序

建议按下面顺序回答复杂问题：

1. 先说业务目标。
2. 再说技术方案。
3. 再说为什么这样设计。
4. 再说遇到的问题和取舍。
5. 最后说结果和可优化点。

### 2. 回答示例：为什么使用依赖注入

可以这样回答：

这个项目的编辑器不是单个组件能解决的，它有画布服务、工作区服务、事件总线、快捷键、图层、撤销恢复等多个模块。如果每个模块都自己 import 并 new 其他模块，会导致依赖关系混乱，也不利于后续替换和测试。所以项目使用依赖注入，把服务注册到容器里，需要服务的类通过构造函数声明依赖，由容器统一创建。这样服务边界更清楚，也能创建编辑器级的子容器，方便未来支持多个编辑器实例。

可能追问：依赖注入有没有缺点？

可以回答：有。它会增加理解成本，新手不容易直接看出实例在哪里创建；如果服务依赖关系复杂，也可能出现循环依赖。所以不是所有项目都需要 DI。普通页面可以用普通 import 和组合式函数，但复杂编辑器、多服务协作、需要插件化扩展时，DI 的收益会更明显。

### 3. 回答示例：为什么不用 Pinia 管理全部画布状态

可以这样回答：

Pinia 适合管理业务状态，比如当前工具、字体列表、用户信息等。但 Leafer 的画布对象是复杂实例，包含大量方法、事件、内部状态和可能的循环引用。如果全部放进 Pinia，会被响应式系统代理，带来性能和行为风险。因此项目只把轻量业务状态放进 Pinia，把画布实例、contentFrame、activeObject 等核心画布状态放在 `MLeaferCanvas` 服务里，并用 shallowRef 暴露必要响应式引用。

### 4. 回答示例：PSD 导入难点

可以这样回答：

PSD 导入的难点不是读文件本身，而是格式转换。`ag-psd` 可以把 PSD 解析成图层数据，但 Photoshop 的图层属性和 Leafer 的画布对象不是一一对应的。比如文本要区分普通文本和富文本，字体大小还要考虑 transform 缩放，颜色要做格式转换，描边、段落对齐、下划线、删除线、分组、蒙版都要映射到编辑器支持的属性。并且字体加载不完整时，导入后的视觉效果会和 PSD 有偏差，所以导入后还要提取字体并触发重新渲染。

### 5. 回答示例：多页面如何实现

可以这样回答：

多页面通过 WorkspacesService 和 MLeaferCanvas 协作实现。WorkspacesService 管理页面 id 和名称，MLeaferCanvas 用 Map 保存每个页面对应的 JSON。切换页面时，工作区服务先发 `workspaceChangeBefore`，画布服务监听后把当前 contentFrame 转成 JSON 保存；然后工作区服务更新 currentId 并发 `workspaceChangeAfter`，画布服务再清空当前画布并导入目标页面 JSON。这样工作区服务不需要知道画布细节，画布服务也不需要直接管理 UI 点击逻辑。
