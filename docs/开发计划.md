# 精准到文件的底层架构开发与测试计划

> [!NOTE]
> 这是一份精确到具体物理文件级别的架构复刻手册。按照从没有任何依赖的最底层工具开始，一直到顶层的 Vue 桥接，遵循**自下而上（Bottom-Up）**的开发顺序。

---

## 阶段一：纯基础工具箱 (Pure Utilities)

这一层完全无业务依赖，只处理数据结构和内存管理。所有的文件存放在 `src/utils/` 目录下。

### 1. `src/utils/linkedList.ts`
- **核心导出**：`class LinkedList<E>`
- **开发要求**：实现一个双向链表。必须使用 `Node.Undefined` 替代 `null` 作为首尾哨兵。重点实现 `push()` 和 `unshift()` 方法，它们必须返回一个能在 $O(1)$ 时间复杂度内移除自身的闭包函数：`() => void`。
- **对应测试文件**：`tests/utils/linkedList.test.ts`
  - **测试用例 1**：测试 `push` 和 `pop` 的 LIFO 顺序，断言 `size` 正确。
  - **测试用例 2**：连续插入 3 个元素，保存第二个元素 `push` 时返回的移除函数。调用该移除函数，断言链表中元素 2 消失且首尾拼接正确，断言复杂度（不可遍历）。

### 2. `src/utils/lifecycle.ts`
- **核心导出**：`interface IDisposable`, `function dispose()`, `class DisposableStore`, `class Disposable`
- **开发要求**：整个应用防止内存泄露的核心。`DisposableStore` 需要使用 `Set` 收集对象，`Disposable` 需提供受保护的 `this._register()`。
- **对应测试文件**：`tests/utils/lifecycle.test.ts`
  - **测试用例 1**：测试 `dispose` 函数传入数组时，若其中某对象 `dispose` 抛出异常，断言后续对象依然会被销毁，且最后抛出 `MultiDisposeError`。
  - **测试用例 2**：`DisposableStore.dispose()` 被调用后，如果再次向该 store 执行 `add()`，断言新加入的对象会立即报错或立即被 `dispose`。

### 3. `src/utils/event.ts`
- **核心导出**：`interface Event<T>`, `class Emitter<T>`
- **开发要求**：依赖前两个文件，构建观察者模式。内部订阅列表必须使用 `LinkedList` 存储。调用 `.event(callback)` 时，返回一个 `IDisposable`（底层其实就是 `LinkedList` 的移除闭包）。
- **对应测试文件**：`tests/utils/event.test.ts`
  - **测试用例 1**：测试 `emitter.fire(data)`，断言所有的 listener 都能同步收到 `data`。
  - **测试用例 2**：调用返回的 `IDisposable.dispose()` 后，断言对应的 listener 不再收到 `fire` 通知。

### 4. `src/utils/async.ts`
- **核心导出**：`runWhenIdle()`, `class IdleValue<T>`
- **开发要求**：如果环境支持 `requestIdleCallback` 就用它，不支持则降级用 `setTimeout` 模拟帧。`IdleValue` 在实例化时就静默开始任务，当调用 `get value` 时，若未完成，必须取消调度并同步执行返回结果。
- **对应测试文件**：`tests/utils/async.test.ts`
  - **测试用例 1 (空闲执行)**：使用 Mock 模拟系统空闲，断言 `IdleValue` 在不阻塞主线程的情况下算出结果并缓存。
  - **测试用例 2 (紧急执行)**：创建 `IdleValue` 之后立刻取值，断言其同步取消异步回调并直接计算。

## 阶段二：核心依赖注入引擎 (DI Core Engine)

这一层处理面向接口编程（IoC）的逻辑，所有文件放在 `src/core/instantiation/` 下。

### 5. `src/core/instantiation/graph.ts`
- **核心导出**：`class Graph<T>`
- **开发要求**：实现一个有向图结构。需要有节点（Node）和边（Edge），用于描述服务之间的依赖关系，核心方法是 `findCycleSlow()`。
- **对应测试文件**：`tests/core/graph.test.ts`
  - **测试用例**：故意制造环（A -> B -> C -> A），断言 `findCycleSlow()` 能够成功检测出回路路径。

### 6. `src/core/instantiation/descriptors.ts`
- **核心导出**：`class SyncDescriptor<T>`
- **开发要求**：非常简单，仅保存一个类的构造函数（Ctor）、额外的静态参数（staticArguments）和一个布尔值（是否支持延迟实例化）。无需测试文件。

### 7. `src/core/instantiation/instantiation.ts`
- **核心导出**：`ServiceIdentifier<T>`, `createDecorator<T>()`, `IInstantiationService` 接口
- **开发要求**：利用 TypeScript 的 Decorator（如 `@ILogService`）。`createDecorator` 函数通过存取 `ServiceIdentifier` 来关联接口与实现。主要为类型与常量声明，无需测试文件。

### 8. `src/core/instantiation/serviceCollection.ts`
- **核心导出**：`class ServiceCollection`
- **开发要求**：内部维护一个 Map。对外提供 `set(id, instanceOrDescriptor)` 和 `get(id)`。
- **对应测试文件**：`tests/core/serviceCollection.test.ts`
  - **测试用例**：简单测试对描述符（Descriptor）或真实实例的 set 和 get。

### 9. `src/core/instantiation/instantiationService.ts`
- **核心导出**：`class InstantiationService`
- **开发要求**：整个引擎的心脏。实现 `invokeFunction()` 和 `createInstance()`。
  - 在 `createInstance` 中获取构造函数上的元数据（Dependencies），如果依赖没注册就抛错，如果注册了就从自己或父级提取，或者顺着依赖图递归实例化。
  - 需要利用 `Proxy` 和前面的 `IdleValue` 实现**延迟实例化 (Delayed Instantiation)**，并拦截前置的 Event 监听 (`earlyListeners`)。
- **对应测试文件**：`tests/core/instantiationService.test.ts`
  - **测试用例 1 (即时依赖解析)**：定义服务A和服务B，B通过装饰器依赖A，测试能否正确 `createInstance(B)` 并且内部获取到 A。
  - **测试用例 2 (循环依赖)**：制造 A、B 的互相依赖，断言实例化时抛出循环依赖异常。
  - **测试用例 3 (延迟实例化)**：注册服务 C 时带上 `SyncDescriptor(C, [], true)`。断言其未被实际创建（如全局计数器没有增加）。
  - **测试用例 4 (提早事件绑定)**：在 C 未实例化时，通过代理调用 `C.onDidSomething()` 绑定事件。然后调用 `C.doWork()` 触发紧急实例化，断言之前的事件监听被成功迁移并触发。

## 阶段三：核心基础服务层 (Base Services)

这一层包含让编辑器跑起来的基础支撑。文件存放在 `src/core/services/`。

### 10. `src/core/services/logService.ts`
- **核心导出**：`ILogService` (装饰器 ID), `class LogService` (具体实现)
- **开发要求**：继承 `Disposable`，封装各种级别的日志输出（trace, debug, info, error）。
- **对应测试文件**：`tests/services/logService.test.ts`
  - **测试用例**：通过 DI 获取实例后，测试各种级别的打印是否被正确拦截或输出到控制台。

### 11. `src/core/createCore.ts`
- **核心导出**：`function createCore()` 或者 `class EditorCore`
- **开发要求**：初始化全局的 `ServiceCollection`，把 `LogService`、`StorageService` 等塞入 `SyncDescriptor` 并注册。然后 `new InstantiationService(services)` 返回全局的依赖注入容器（Root Container）。
- **对应测试文件**：`tests/core/createCore.test.ts`
  - **测试用例**：调用启动函数后，断言返回的容器是否具备解析基础服务的能力。

## 阶段四：UI 框架桥接 (Vue Integration)

在此将上述纯 TypeScript 引擎引入 Vue 视图层。文件放在 `src/hooks/` 和 `src/main.ts`。

### 12. `src/main.ts` (或顶级入口文件)
- **开发要求**：调用 `createCore()` 获取 `instantiationService`。然后通过 Vue 的全局依赖注入 `app.provide('IInstantiationService', instantiationService)` 挂载到整个 Vue 应用。

### 13. `src/hooks/useService.ts`
- **核心导出**：`export function useService<T>(id: ServiceIdentifier<T>): T`
- **开发要求**：
  ```typescript
  import { inject } from 'vue';
  export function useService<T>(id: ServiceIdentifier<T>): T {
    const di = inject('IInstantiationService');
    return di.invokeFunction(accessor => accessor.get(id));
  }
  ```
- **对应测试文件**：`tests/hooks/useService.test.ts` (基于 Vue Test Utils)
  - **测试用例**：创建一个 Vue 组件并在其中使用 `useService(ILogService)`，使用 `mount` 并 `global.provide` 传入 Mock 容器，断言组件渲染成功且日志服务被正确获取。

## 阶段五：业务服务与视图 (Feature Modules)

最后是基于以上基建开发您自己的编辑器特性。以图层服务为例：

### 14. `src/features/layer/layerService.ts`
- **核心导出**：`ILayerService`, `class LayerService`
- **开发要求**：继承自 `Disposable`，注入其他的服务。内部可能有一个 `layers` 数组，并暴露 `onDidLayerChange` 事件（基于 `Emitter`）。对外提供 `addLayer()`, `removeLayer()`。
- **对应测试文件**：`tests/features/layerService.test.ts`
  - **测试用例**：测试 `addLayer` 调用时，`onDidLayerChange` 是否正确发送了事件；测试调用自身 `dispose` 后，其内部维护的数组和事件是否被销毁。

### 15. `src/features/layer/components/LayerPanel.vue`
- **开发要求**：不再使用 Pinia / Vuex 等状态库。在 `<script setup>` 中：
  ```ts
  const layerService = useService(ILayerService);
  const layers = ref([]);
  
  // 监听服务抛出的纯事件并更新 Vue 的响应式状态
  const disposable = layerService.onDidLayerChange(newLayers => {
    layers.value = newLayers;
  });
  
  // 利用 Vue 生命周期和前期的销毁机制结合
  onUnmounted(() => disposable.dispose());
  ```
- **对应测试文件**：E2E 或组件集成测试，断言点击面板增加图层时，UI 是否正确渲染并销毁监听。
